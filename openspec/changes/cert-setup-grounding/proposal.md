## Why

Primary-target certs ship as human-verified seed data (`certifications`), but SPEC → Certification Setup & Grounding and PRD §4 / J5 require an admin to add a **new or unlisted** cert without code changes — and to do it safely. The admin is often a learner who cannot validate exam-format facts (question count, passing score, time limit, domains and weights) from memory, yet those facts drive readiness scoring, mock-exam format, and agent context, so they must be trustworthy. Today there is no API to discover where to fetch the official exam guide, confirm the source, or extract those fields **with citations** so accept/reject is a meaningful, source-checkable action rather than a rubber stamp. There is also no surfacing of certs whose metadata has aged past a staleness interval and is **due for re-verification**. This change builds that backend; the Phase 10 `web-admin` cert-setup UI consumes it.

## What Changes

- Add a `CertSetupModule` (admin-facing) in `apps/api`, mounted under `/api/v1/admin/certifications/*`, protected by the global `JwtAuthGuard` + `@Roles('admin')` (`RolesGuard`).
- **Source discovery** — `POST /api/v1/admin/certifications/discover-sources` { name, code? }: run a web-search tool through the `llm-foundation` gateway (existing tool-capable streaming method, `certification-prefill` task type), rank vendor-domain candidates first, and return candidate official-guide URLs (and suggested content sources) for admin review. Read-only; nothing persisted; the model never fabricates a URL.
- **Admin source confirm + grounded per-field extraction** — `POST /api/v1/admin/certifications/extract` { name, code?, confirmedSourceUrl }: enqueue a worker job that fetches the confirmed source via the existing scrapper sidecar and extracts each exam-format field (domains+weights, questionCount, passingScore, timeLimitMinutes) under the grounding contract — every grounded field carries a `passage` that is a **verbatim** substring of the fetched source (shared extractive-contract validator from `grounding-verification`) and passes an **independent verifier** model call (`answer-verification`, distinct from extraction). Return each field with either a `{ url, passage }` citation or an `{ unverified: true }` flag.
- **Unverified flags** — any field that cannot be grounded is surfaced flagged "unverified — confirm manually", never silently invented. Extend the shared certification-provenance type additively so a per-field value can be a citation, `{ unverified: true }`, or admin `{ manuallyConfirmed: true }` — stored in the existing `provenance` JSON column (no migration).
- **Create grounded draft** — `POST /api/v1/admin/certifications`: create the `Certification` in `state: draft` with the per-field provenance map persisted and `verifiedAt` set, validate domain weights sum to 100, reject duplicate `code`, and write a `cert.created` audit entry. (The coverage-bar auto `draft`→`live` flip is owned by `cert-go-live` and is **out of scope** here.)
- **Re-verification** — `POST /api/v1/admin/certifications/:id/reverify`: rerun the same source-confirm + per-field-citation flow against an existing cert, update fields/provenance, reset `verifiedAt`, and write a `cert.reverified` audit entry (reusing the existing vocabulary value). Re-verification never changes `state`.
- **Due-for-reverification surfacing** — `GET /api/v1/admin/certifications/due-for-reverification` (admin-only) returns certs whose `verifiedAt` is null or older than the configurable `CERT_REVERIFICATION_INTERVAL_DAYS`. The flag is **derived** (no stored column).
- **Worker cron (cross-cutting deliverable, cert half)** — add a scheduled cron in `apps/worker` that scans certs due for re-verification and **surfaces** them (gauge metric of the due count + log). It is distinct from the existing stale-source re-ingestion cron (owned by `content-pipeline`) and modifies no certification.
- **Shared additions** — add `cert.created` to `@readion/shared` `auditActions`; add the cert-extraction cross-app BullMQ queue-name constant; add request/response DTOs + Zod schemas (discover request/response, extract request/result, create/reverify requests, due-list response). Regenerate and commit the Orval client.

This change **orchestrates** existing layers — it does not reimplement source registration (`content-admin`), the scrapper fetch (`content-pipeline`), the grounding contract/verifier discipline (`grounding-verification`), the audit log (`admin`), or the LLM gateway (`llm-foundation`).

## Capabilities

### New Capabilities
- `certification-setup`: Admin grounded setup of new/unlisted certifications — web-search source discovery, admin source confirmation, grounded per-field exam-format extraction with verbatim citations and an independent verifier pass, unverified-field flagging, draft creation with persisted provenance, a re-verification flow, and a staleness-driven "due for re-verification" surface (API + worker cron). Every privileged action is written to the append-only audit log.

## Impact

- **New code**: `apps/api/src/cert-setup/` (module, controller, service, discovery service, extraction-orchestration/job producer, provenance + DTO mappers, due-for-reverification read model). `apps/worker/src/content-pipeline/` cert-extraction processor + `cron/cert-reverification.cron.ts` + its metric. New Zod schemas/DTOs, `cert.created` audit action, cert-extraction queue-name constant, and per-field provenance type extension in `packages/shared`. New `CERT_REVERIFICATION_INTERVAL_DAYS` env value in the api + worker Zod schemas. Regenerated Orval client under `apps/web/src/api/`.
- **Reused, not modified**: `Certification` entity + `certifications` table and `CertificationsService`/repository (`certifications`); `ContentSource` registration via `content-source-admin` endpoints (`content-admin`); the scrapper sidecar client + ingestion plumbing (`content-pipeline`); the shared extractive-contract validator + independent-verifier discipline (`grounding-verification`); `AuditLog` + `AuditLogService` (`admin`); the `llm-foundation` gateway (`certification-prefill`, `answer-verification` task types); `JwtAuthGuard`/`RolesGuard`/`@Roles` (`auth`).
- **No new entity, no new migration** — per the Entity ownership table, `cert-setup-grounding` owns no entity (like `cert-go-live`). Source URLs, citations, and unverified/manual flags live in the existing `provenance` JSON column; the due-for-reverification flag is derived from `verifiedAt`; the only schema-shaped touch is additive shared types over JSON columns.
- **Cross-cutting deliverable owned**: the cert "due for re-verification" worker cron + its gauge metric (the stale-source re-ingestion cron remains `content-pipeline`'s).
- **Dependencies**: `certifications`, `content-pipeline`, `llm-foundation`, `content-admin`, `admin` — all archived/implemented. The Phase 10 `web-admin` UI depends on this API.
