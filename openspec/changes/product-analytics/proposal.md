## Why

The SPEC's `observability` change stands up *operational* telemetry — HTTP/LLM latency, verifier pass/fail, queue depth, active-session count, agent SSE error rate, ingestion counts — as aggregate Prometheus series. None of that answers the **product** questions PRD §3 makes the bar for "is this working": is a user *active*, is their readiness *improving*, are they *retained*, do they *finish* sessions, do they *use the tutor*, and is the per-user LLM cost inside the guardrail. Those are derived, per-user, cohorted metrics that Prometheus labels can't carry (per-user cardinality) and that no current change computes.

`product-analytics` is the success-metric instrumentation that closes that gap (roadmap Phase 9; Spec ref PRD §3 → Success metrics, Definitions & targets, Guardrail metrics). It introduces **no new entity** — every metric is a derived read model over tables other changes already own (roadmap Entity ownership note: "No new entities are introduced by … `product-analytics` (derived read models over existing tables)"). It surfaces those read models through an **admin-only product-analytics dashboard** endpoint, each metric shown against its v1 target so an admin can see at a glance whether the product is hitting the bar.

Concrete requirements pulled from PRD §3 (the Spec ref), not the one-line Scope:

- **Active user** = a user who has completed **≥ 2 study sessions in the trailing 14 days** (PRD §3 → Definitions & targets). This definition gates almost every other metric (north-star, sessions/week, LLM cost are all *per active user*).
- **North-star** = **median readiness-score gain per active user** over a window (PRD §3 table: "per 2-week window"; target: "median readiness gain over first 4 weeks of active use ≥ +15"). Readiness is the `ReadinessService` value (SPEC → Exam Readiness Score).
- **Supporting** — sessions completed per active user per week (target median ≥ 2); week-2 and week-4 retention (target W4 ≥ 40%); session completion rate, started → end-of-session summary (target ≥ 75%); agent engagement rate, sessions with ≥ 1 agent interaction (target ≥ 50%).
- **Guardrail** — **LLM cost per active user** per month (target: within budget). PRD also names agent/SSE error rate and content-ingestion success rate as guardrails — but those are already emitted as ops Prometheus series (agent change: "Agent SSE error rate is observable"; `observability`/`content-pipeline`: ingestion counts), so this change does **not** re-derive them; the Scope is explicitly "metrics the SPEC's ops metrics don't cover."
- **Outcome (lagging)** — self-reported real-exam pass rate, "tracked but not optimized in v1" (PRD §3). The raw signal is the `exam_outcome_response` already captured per enrollment by `email-lifecycle`.

## What Changes

- **`AnalyticsModule` (`apps/api`, admin-only)** — a new feature module exposing `GET /api/v1/admin/analytics/overview`, protected by the global `JwtAuthGuard` and `@Roles('admin')` (the established admin pattern from `admin`). It returns, in the standard `{ data }` envelope, the full product dashboard read model over a configurable reporting window: active-user count, north-star median readiness gain, median sessions/week, W2/W4 retention, session-completion rate, agent-engagement rate, the LLM-cost-per-active-user guardrail proxy, and the lagging self-reported pass-rate breakdown — each paired with its configured **v1 target** so the dashboard renders metric-vs-target. Non-admins get `403`, unauthenticated `401`.
- **Active-user read model** — a query over `StudySession` counting users with ≥ `ANALYTICS_ACTIVE_MIN_SESSIONS` (default 2) terminal-completed sessions whose `endedAt` falls in the trailing `ANALYTICS_ACTIVE_WINDOW_DAYS` (default 14). This set is the denominator/population for the per-active-user metrics.
- **North-star read model** — for each active user, readiness *gain* = readiness now − readiness at the start of the `ANALYTICS_NORTHSTAR_WINDOW_DAYS` window (default 28, matching the +15/4-week target), reported as the **median** across active users. Because readiness is a read-through value with **no history table** (SPEC → Exam Readiness Score; readiness spec forbids a readiness entity), the as-of value is recomputed from the immutable, timestamped `QuizResponse` / `MockExam` rows that already drive readiness — a derived read model over existing tables, not a new snapshot entity (see design.md for this central tension).
- **Sessions/week, completion-rate, agent-engagement read models** — aggregates over `StudySession` (started vs reached-summary vs abandoned), and `StudySession ⟕ AgentConversation/AgentMessage` for "≥ 1 agent interaction" (a session-linked conversation with ≥ 1 `role: user` message).
- **Retention read model** — registration-week cohorts over `User.createdAt`; W2/W4 = the fraction of a cohort that still meets the active-user definition in the 2nd / 4th week after registration.
- **LLM-cost-per-active-user guardrail (derived proxy)** — there is **no persisted per-user token/cost** (the LLM gateway emits token usage only as aggregate Prometheus series labelled by model/use-case). The proxy attributes cost from countable LLM-driven artifacts per active user — `QuizResponse` count, `MockExam` question count, session-item generations, and `AgentMessage` assistant/tool rows — multiplied by configured per-task cost coefficients (`ANALYTICS_COST_*`), divided by the active-user count. This is a budget-tracking estimate, not exact billing (see design.md / Open Questions).
- **Lagging pass-rate read model** — counts of `exam_outcome_response` (`passed` / `did_not_pass` / `not_yet` / `dismissed`) on `user_certifications`, reported as a self-reported pass-rate breakdown that is displayed but never fed into any other metric. This reads columns owned by `email-lifecycle` (see Impact → soft dependency).
- **Config (Zod, fail-fast, `apps/api`)** — `ANALYTICS_ACTIVE_WINDOW_DAYS` (14), `ANALYTICS_ACTIVE_MIN_SESSIONS` (2), `ANALYTICS_NORTHSTAR_WINDOW_DAYS` (28), the per-task cost coefficients `ANALYTICS_COST_QUIZ`, `ANALYTICS_COST_MOCK_QUESTION`, `ANALYTICS_COST_SESSION_ITEM`, `ANALYTICS_COST_AGENT_MESSAGE`, and the v1 targets `ANALYTICS_TARGET_NORTHSTAR_GAIN` (15), `ANALYTICS_TARGET_SESSIONS_PER_WEEK` (2), `ANALYTICS_TARGET_W4_RETENTION` (0.40), `ANALYTICS_TARGET_COMPLETION_RATE` (0.75), `ANALYTICS_TARGET_AGENT_ENGAGEMENT` (0.50), `ANALYTICS_LLM_COST_BUDGET` (the monthly per-active-user budget). All added to `apps/api/.env.example`.

### Migrations (no new entity)

Per the Entity Ownership table this change **owns no entity** and **introduces no migration**: every metric is computed read-through over existing tables (`StudySession`, `QuizResponse`, `MockExam`, `AgentConversation`/`AgentMessage`, `User`, `UserCertification`). Read-optimizing indexes are intentionally **not** added in v1 (small active-user population, matching the `email-lifecycle` "v1 population is small" reasoning); if profiling later warrants covering indexes they may be added via this change's own non-owning migration without altering any entity's semantics. This is recorded as a deferred non-blocking note, not v1 scope.

## Capabilities

### New Capabilities
- `product-analytics`: An admin-only product-metrics dashboard read model layered over existing study/agent/readiness data. Defines the active-user population (≥ 2 completed sessions / 14 days) and derives, against configured v1 targets, the north-star median readiness-gain-per-active-user, median sessions/week, week-2/week-4 retention cohorts, session-completion rate (started → summary), agent-engagement rate, the LLM-cost-per-active-user guardrail (a coefficient-based proxy, since no per-user token cost is persisted), and the lagging self-reported pass-rate breakdown. Owns no entity and adds no migration; readiness "gain" is recomputed as-of window boundaries from the timestamped quiz/mock rows that already drive readiness.

## Impact

- **apps/api**: new `AnalyticsModule` — `analytics.service.ts` (the read-model computations, reusing `ReadinessService.compute` and repository queries over `StudySession`/`QuizResponse`/`MockExam`/`AgentConversation`/`UserCertification`), `analytics.controller.ts` (`GET /api/v1/admin/analytics/overview`, `@Roles('admin')`), DTOs for the overview envelope, plus the new analytics Zod config group and `.env.example` keys.
- **apps/worker**: none. The roadmap assigns this change **no worker cron**; metrics are computed on-demand per dashboard request (optionally short-TTL Redis-cached). No scheduled processor is introduced.
- **packages/db**: none — no new entity, no migration.
- **packages/shared**: DTO/types for the analytics overview read model and the metric/target pairs; new env-schema keys for `apps/api`; constants for the active-user/north-star window defaults and the exam-outcome response set reused from `lifecycle-email`.
- **apps/web**: the new admin endpoint surfaces in the Orval client (consumed by the later `web-admin` page's product dashboard); no UI in this change.
- **Entities owned**: none (per the Entity Ownership table). Adds no migration.
- **Cross-cutting**: no worker cron is attributed to this change in the roadmap. The roadmap "Feature-emitted metrics" note attributes no specific Prometheus series here either; an opportunistic gauge (e.g. active-user count, north-star gain) MAY be emitted against the existing `observability` infra when the overview is computed, but the dashboard read model is the primary deliverable. The agent/SSE-error-rate and ingestion-success guardrails are already emitted by `agent`/`observability` and are surfaced by reference, not re-derived.
- **Depends on (all archived)**: `sessions` (`StudySession` status/`startedAt`/`endedAt`, completion semantics), `agent` (`AgentConversation`/`AgentMessage` for engagement), `readiness` (`ReadinessService.compute`, calibration semantics). Also reads `QuizResponse` (`quiz`), `MockExam` (`mock-exam`), `User`/`UserCertification` (`auth`/`user-certifications`) — all archived.
- **Soft dependency flagged**: the lagging pass-rate read model reads `exam_outcome_response` on `user_certifications`, captured by **`email-lifecycle`** (same Phase 9). The roadmap dependency graph has **no edge `email-lifecycle --> product-analytics`** (declared Depends on is only `sessions`, `agent`, `readiness`). `email-lifecycle` is already archived so the columns exist; this is flagged for a roadmap-edge addition. If the edge is rejected, the lagging metric degrades gracefully (reports zeros / "no data") rather than failing.
- **Unblocks**: the product-dashboard surface in `web-admin`; no further backend change depends on this one.
