## Why

A new enrollment has no weak-area or readiness signal until several real sessions accumulate, so the first study session is generic and the dashboard reads "not yet calibrated" — undercutting the core promise for a time-constrained learner. SPEC → Diagnostic Exam closes this cold-start gap with a short (10–15 question) breadth calibration offered at enrollment that seeds the enrollment's baseline. The shared timed-exam infrastructure (`MockExam` entity, scoring, domain breakdown, review mode) already landed with `mock-exam`, which deliberately deferred the diagnostic create flow to this change.

## What Changes

- **Diagnostic create flow** — `POST /api/v1/user-certifications/:id/diagnostic` creates a `MockExam` with `type: diagnostic` for the enrollment and enqueues generation. Offered only for **live** certifications (which already meet the per-domain content-coverage bar, guaranteeing every domain has chunks). Reuses the `MockExam` entity owned by `mock-exam` — **no new entity**.
- **Breadth planner** — diagnostic generation allocates a small fixed budget (`DIAGNOSTIC_QUESTION_COUNT`, default 12, range 10–15) for **breadth**: every domain is probed **at least once**, with remaining slots distributed by each domain's exam-share weight (largest-remainder). This differs from the mock planner, which allocates the cert's full question count proportionally with no per-domain floor. Generation reuses the existing grounded + verified quiz pipeline (`QuizService.generate`, the LLM response cache, explanation generation) under the same verifier guarantee as quizzes and mocks.
- **Lenient / optional timer** — the diagnostic shares the mock taking/answer/resume/review machinery but is **not pass/fail** and imposes **no enforced wall-clock deadline**: on generation completion `startedAt` is stamped but `deadline` stays null. Consequently the existing mock auto-submit cron (which sweeps attempts whose `deadline` has passed) never auto-submits a diagnostic, so **abandoning a diagnostic mid-way is treated as a skip** (it is never finalized, never seeds) per SPEC. Taking, answering, submitting, and reviewing reuse the existing `GET /mock-exams/:id`, `PUT /mock-exams/:id/answers/:questionIndex`, and `POST /mock-exams/:id/submit` endpoints (they operate by attempt id regardless of `type`); no new taking/review screens or endpoints.
- **Low-weight seeding on completion** — submitting a diagnostic finalizes the attempt (reusing the shared scorer + `finalizeAttempt`), which emits one enrollment-scoped `QuizResponse` per question and drives `WeakAreasService.recompute`, establishing the initial per-domain `WeakArea` map. The diagnostic finalize additionally emits one `QUIZ_ANSWERED_EVENT` per question so the existing `spaced-repetition` accrual seeds the **review queue** from diagnostic misses (SPEC: "Diagnostic-exam misses seed the queue, giving review signal from day one"). A completed diagnostic satisfies the `exam-readiness` calibration gate immediately (already honored there), flipping readiness from "not yet calibrated" to a number.
- **Diagnostic seeds readiness at LOW weight** — SPEC requires the diagnostic to enter readiness with low weight and decay quickly, whereas real mocks enter with higher weight. The current `exam-readiness` calculator folds **all** submitted/expired `MockExam`s (including `type: diagnostic`) into the higher-weight mock blend. This change modifies `exam-readiness` so `type: diagnostic` attempts are **excluded** from the higher-weight mock blend; the diagnostic instead contributes only through the recency-decayed `WeakArea` path, which is the SPEC-intended "low weight, fast decay."
- **Onboarding offer + re-prompt** — `GET /api/v1/user-certifications/:id/diagnostic-offer` returns whether to offer the diagnostic and in which mode: `onboarding` (fresh, uncalibrated, live cert, no completed diagnostic), `re-prompt` (still uncalibrated after the first session or two, not yet re-prompted), or `none`. `POST /api/v1/user-certifications/:id/diagnostic-offer/dismiss` records that the one-time re-prompt has been shown so it is **re-prompted once** per SPEC. The web onboarding/dashboard UI that renders these is downstream (`web-onboarding`); this change owns only the backend offer/re-prompt logic.
- **Re-taking** — re-running the diagnostic creates a fresh `type: diagnostic` attempt; its finalize emits new `QuizResponse`s that the idempotent `WeakAreasService.recompute` aggregates alongside accumulated real session/mock data, so it **re-seeds the diagnostic contribution without wiping** real history (SPEC).
- All diagnostic resources enforce repository-layer ownership scoping on `userId`; cross-user access returns `404`.

## Capabilities

### New Capabilities
- `diagnostic-exam`: the diagnostic create flow (`type: diagnostic` `MockExam`, live-cert-only), the breadth planner (every domain ≥ 1, remaining slots by exam-share weight, small fixed budget), diagnostic generation reusing the verified quiz pipeline, the lenient/optional-timer lifecycle (no enforced deadline → abandonment = skip), low-weight seeding of weak-areas / readiness / review on completion (emitting `QuizResponse`s + `QUIZ_ANSWERED_EVENT`s and driving `WeakAreasService.recompute`), re-take re-seeding, and the onboarding offer + one-time re-prompt read model and dismiss action.

### Modified Capabilities
- `exam-readiness`: exclude `type: diagnostic` `MockExam`s from the higher-weighted mock blend so a diagnostic seeds readiness at low weight (via the recency-decayed `WeakArea` path) and decays quickly, per SPEC — distinct from real mocks, which keep their higher weight. The diagnostic calibration gate is unchanged (already honored).
- `mock-exam`: generalize the generation-complete / "ready" derivation so a completed attempt with a null `deadline` (the optional-timer diagnostic) reports `generation: ready` with no countdown instead of being stuck `preparing`; branch generation by `type` (breadth planner + diagnostic budget for `diagnostic`, unchanged proportional planner for `mock`); and suppress pass/fail framing for `type: diagnostic` on finalize and in the response. No change to the `mock` create/timer/scoring behavior.

## Impact

- **Entities owned (new table + migration):** none. The diagnostic reuses the `MockExam` entity owned by `mock-exam` (its `type` enum already includes `diagnostic`). The only schema change is a column extension: a nullable `diagnosticRePromptedAt` timestamp added to `UserCertification` (owned by `user-certifications`) via this change's own migration, backing the one-time re-prompt — consistent with the entity-ownership rule that a later change may extend an existing entity with its own migration. No new entity, per the entity-ownership table ("diagnostic variant adds no new entity").
- **API:** new endpoints under `/api/v1` — create a diagnostic for an enrollment, read the diagnostic offer/re-prompt state, dismiss the re-prompt. Taking/answering/submitting/reviewing reuse the existing mock-exam endpoints. Orval client regenerated and committed.
- **Generation:** the diagnostic breadth planner + diagnostic budget added to the shared generation path in `apps/api` (where the verified quiz pipeline lives, per the `mock-exam` revision), branching on `attempt.type`. Generation reuses `QuizService.generate`, the LLM response cache, and explanation generation.
- **Config:** `DIAGNOSTIC_QUESTION_COUNT` (default 12) and `DIAGNOSTIC_REPROMPT_AFTER_SESSIONS` (default 1) — Zod-validated `@nestjs/config`.
- **Worker crons:** none. The cross-cutting cron table assigns no cron to `diagnostic`; the diagnostic is deliberately excluded from the existing `mock-exam` auto-submit cron (abandonment = skip).
- **Metrics:** none diagnostic-specific in SPEC → Observability → Metrics; diagnostic generation reuses the verified quiz pipeline, so verifier pass/fail and regeneration/substitution metrics already emit from that shared path.
- **Depends on:** `mock-exam` (`MockExam` entity + `type: diagnostic` enum, shared scorer / `finalizeAttempt` / answer / submit / review / generation infrastructure), `weak-areas` (`WeakAreasService.recompute`), `readiness` (`ReadinessService.compute` + the diagnostic calibration gate; modified here for low-weight), `review-srs` (the `QUIZ_ANSWERED_EVENT`-driven `spaced-repetition` accrual). All archived.
- **Consumed downstream by:** `web-onboarding` (renders the diagnostic offer/re-prompt and the diagnostic take/review using the mock-exam UI components), `end-of-session-summary` (post-diagnostic seeding feeds the same readiness/weak-area surfaces).
- **Boundaries kept out of scope:** all frontend (`web-onboarding`, `web-mock-exam` components), the `mock` create/timer/scoring behavior (`mock-exam`), the readiness formula internals beyond the diagnostic-weighting exclusion (`readiness`), and quiz generation/verification internals (`quiz` / `grounding-verification`).
